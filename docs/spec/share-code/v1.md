# Share code v1

Status: **draft**. It is frozen once the first implementation passes all
vectors.

Share-code version `S = 1`. This spec defines how a game descriptor
(rules version, mode, seed) and an optional result (score, reached) are
encoded as bytes, as a text code, as a QR code and as a link.
Conformance vectors: `docs/spec/test-vectors/share-code/v1/`.

## 1. Record (bytes)

All multi-byte integers are big-endian.

| offset | size | field | meaning |
|---|---|---|---|
| 0 | 1 | `S` | share-code version, `1` |
| 1 | 1 | `R` | rules version (1–255) |
| 2 | 1 | `mode` | mode id as defined by rules `R` (1–255) |
| 3 | 8 | `seed` | u64 PRNG seed |
| 11 | 1 | `flags` | bit 0: a result follows. Bits 1–7 must be 0 |
| 12 | 2 | `score` | only if flags bit 0 is set: u16 |
| 14 | 2 | `reached` | only if flags bit 0 is set: u16 |
| end−2 | 2 | `crc` | CRC-16 over all preceding bytes (offset 0 up to the CRC) |

The total length is **14 bytes** without a result and **18 bytes** with
one. Score and reached are clamped to 65535 when encoding.

CRC-16 is the CCITT-FALSE variant: polynomial `0x1021`, init `0xFFFF`, no
input or output reflection, xorout `0x0000`. Its check value for ASCII
`"123456789"` is `0x29B1`.

A share-code reader does **not** decide whether `mode` and `R` are playable.
That is up to the app's rules support (decision 0007). It must still decode
them, so it can say "needs a newer version".

## 2. Text code

```
text := "SY" + decimal(S) + "-" + groups(base32(record[1..]))
```

- `record[1..]`: the record **without** byte 0. `S` is carried by the
  prefix instead.
- `base32`: **Crockford** alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`. Bytes
  form one big-endian bit string, which is cut into 5-bit groups from the
  most significant bit. The last group is padded with **zero** bits. No
  padding characters are used.
  13 bytes give 21 characters, and 17 bytes give 28 characters.
- `groups`: characters in groups of 4, joined by `-`. The last group may be
  shorter.

Examples (rules 1, classic, seed `0x2a`; see the vectors):
- descriptor only: `SY1-040G-0000-0000-001A-03CT-T`
- with result (score 47, reached 48): `SY1-040G-0000-0000-001A-0402-Y01G-J960`

### 2.1 Parsing

Input may be any text (e.g. a whole messenger message). A reader:

1. finds the first match of `SY([0-9]+)-([0-9A-Za-z]+(?:-[0-9A-Za-z]+)*)`,
   case-insensitive;
2. reads `S` from group 1. If `S` is unsupported, it reports
   *unsupported share-code version* (and stops);
3. takes group 2, removes `-`, uppercases it, and maps `O→0`, `I→1`, `L→1`
   (Crockford's decoding aliases). `U` and any other character not in the
   alphabet make the code *invalid*;
4. decodes base32 to bytes. The number of characters must be exactly 21
   or 28, and the padding bits must be zero. Otherwise the code is
   *invalid*;
5. prepends byte `S` and checks the CRC, the flags (unknown bits set →
   *invalid*) and that the length matches flags bit 0.

Whitespace inside the code is **not** accepted. Messengers keep codes on one
line, and this avoids false matches.

## 3. QR code

The QR payload is the **text code in uppercase**, without any message
around it. All of its characters are in the QR *alphanumeric* set, so the
QR code stays small (version 2–3). Error correction level **M**.

## 4. Link

```
stroopy://play?c=<text code>
```

A link is parsed by extracting the `c` parameter and applying §2.1. Apps
should also accept a pasted link as plain text: §2.1 finds the code inside
it anyway.

## 5. Results in codes

When a code carries a result, the receiver shows it as the score to beat,
e.g. "Your friend scored 47 (out at #48)". The result is informational and
not verifiable (see the fairness notes in `docs/design/`).
