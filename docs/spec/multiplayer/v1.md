# Multiplayer v1

Status: **draft**. It is frozen once two implementations have played
against each other and pass all vectors.

Multiplayer version `M = 1`. This spec defines live multiplayer: rooms and
the invitations to them, the messages players exchange, and how they travel
over Nostr relays
([decision 0012](../../decisions/0012-nostr-first-multiplayer.md)). Other
transports (LAN, Bluetooth) will carry the same messages and get their own
invitation entry and section later.
Conformance vectors: `docs/spec/test-vectors/multiplayer/v1/`.

Principle: **the network only reports, it never drives.** Every device
generates the sequence from the descriptor and runs its own timers (rules
`R`). Messages carry who is in the room, which game to play, and how far
everyone got.

## 1. Rooms and invitations

A **room** is a group of players who play the same games one after another.
It is identified by a **room id** of 40 random bits and lives on exactly one
transport. The player who creates the room is its **host**. The host chooses
the mode and starts games. Everybody else is a **guest**.

Players join a room with an **invitation**: the room id plus everything
needed to reach the room (for Nostr: the relays). The creator makes the
invitation when creating the room, and every player in the room may share
it again. There is no shorter form: a room id alone is not enough to join.

### 1.1 Record (bytes)

All multi-byte integers are big-endian.

| offset | size | field | meaning |
|---|---|---|---|
| 0 | 1 | `M` | multiplayer version, `1` |
| 1 | 5 | `room` | room id, 40 random bits |
| 6 | 1 | `K` | number of entries, 1–255 |
| 7 | … | entries | `K × { tag: u8, len: u8, value: len bytes }` |
| end−2 | 2 | `crc` | CRC-16/CCITT-FALSE over all preceding bytes (as in game code v1 §1) |

Each entry says how to reach the room over one transport. Tags:

| tag | transport | value |
|---|---|---|
| 1 | Nostr relay (§3) | UTF-8 relay URL, e.g. `wss://nos.lol` |

- A **Nostr relay** value starts with `wss://` or `ws://` (lower case),
  has at least one character after it, and contains no white space or
  control characters (U+0000–U+0020, U+007F). An invitation holds at most
  **8** relays, and no URL twice.
- Tags `2`–`127` are reserved for future transports. A reader **skips
  unknown tags** (using `len`), so a transport can be added without a new
  multiplayer version, and an older app still joins over the transports it
  knows.
- Tags `128`–`255` are reserved and must not be written.
- A reserved tag `128`–`255`, a relay value that breaks the rules above,
  more than 8 relays, a repeated relay and `K = 0` make the invitation
  *invalid*.
- An invitation without an entry the reader can use (for v1: without a
  Nostr relay) is valid, but the reader reports *no supported transport*.

Writers emit the entries of one transport in the order of preference. In
v1 a writer emits 1–8 Nostr relays and nothing else.

### 1.2 Text code

```
text := "SYM" + decimal(M) + "-" + groups(base32(record[1..]))
```

- `SYM`: `SY` for Stroopy, `M` for multiplayer.
- `base32` and `groups` are the same as in game code v1 §2: Crockford
  alphabet, big-endian bit string, zero padding bits, no padding characters,
  groups of 4 joined by `-`.
- The room id is exactly the first 8 characters after the prefix (40 bits).

Example (room id `796KQTHW`, relay `wss://relay.damus.io`; see the vectors):

```
SYM1-796K-QTHW-040H-8XVK-ECX2-YBVJ-CNP6-2Y9E-CHGP-TXBK-5SMP-YE3E
```

#### Parsing

An invitation with several relays is long, and messengers or mail clients
may wrap it. Input may be any text. A reader:

1. finds the first match of `SYM([0-9]+)-`, case-insensitive;
2. reads `M`. If `M` is unsupported, it reports *unsupported multiplayer
   version* (and stops);
3. collects the characters that follow: it skips `-` and white space, maps
   letters to upper case and the aliases `O→0`, `I→1`, `L→1`, and stops at
   the first character that is then not in the alphabet (or at the end of
   the input);
4. decodes the record **structurally**: `K` and the entry lengths give the
   record length `L`. Exactly the first `ceil((L−1)·8/5)` collected
   characters belong to the code. Further characters are ignored, so text
   after the code does no harm;
5. fails as *invalid* if there are too few characters, if the padding bits
   of the last used character are not zero, if the CRC doesn't match, or if
   an entry is invalid (§1.1);
6. reports *no supported transport* if no entry is usable (§1.1).

### 1.3 QR code

The QR payload is the **text code in uppercase**, without any message
around it. Its characters are all in the QR *alphanumeric* set. Error
correction level **M**.

### 1.4 Link

```
stroopy://join?c=<text code>
```

A link is parsed by extracting the `c` parameter and applying §1.2. Apps
also accept a pasted link as plain text: §1.2 finds the code inside it.

## 2. Messages

Messages are JSON objects (UTF-8). Every message has `"m": 1` and a `type`.
A receiver ignores messages with another `m`, unknown `type`s and unknown
fields. A message with a missing or mistyped required field is ignored.

A player is identified by the **sender key** of the transport (§3: the Nostr
public key), not by a field in the message.

### 2.1 `status`

Each player's complete state. Sent:
- when joining the room,
- every **5 s** (heartbeat),
- when the state changes, but no more often than every **500 ms** (the
  latest state is sent when the interval has passed),
- immediately when the player's game ends.

```json
{"m":1,"type":"status","name":"Ann","host":true,"rules":[1],"mode":1,
 "game":{"code":"SYG1-040G-0000-0000-001A-03CT-T","n":12,"score":11,"over":false}}
```

| field | type | meaning |
|---|---|---|
| `name` | string | player name, 1–24 characters, no control characters (see below) |
| `host` | bool | the sender is the host |
| `rules` | array of int | rules versions the sender can play |
| `mode` | int | host only: mode selected for the next game. Optional for guests |
| `game` | object | optional; the sender's current or last game in this room |
| `game.code` | string | the game's game code without result (game code v1) |
| `game.n` | int | item/round shown now; when over: `reached` (rules §6) |
| `game.score` | int | current score; when over: final score |
| `game.over` | bool | the game has ended for this player |

`game` is omitted until the player has started a game in this room.

Validation: `name` is a string, `host` a bool, `rules` a non-empty array of
integers 1–255, `mode` (if present) an integer 1–255; `game` (if present)
has a string `code`, non-negative integers `n` and `score`, and a bool
`over`. Otherwise the message is ignored. A receiver cleans `name`: it removes
control characters (U+0000–U+001F, U+007F), trims white space and keeps
at most 24 Unicode code points. An empty result becomes `?`.

### 2.2 `start`

Sent by the **host** to start a game.

```json
{"m":1,"type":"start","code":"SYG1-040G-0000-0000-001A-03CT-T"}
```

`code` is a game code without result (receivers ignore a `start` whose
`code` doesn't decode or carries a result, and one whose rules or mode they
can't play). Its seed is chosen at random by the
host. The host sends `start` only when it isn't playing itself, and starts
its own countdown when sending.

### 2.3 `bye`

```json
{"m":1,"type":"bye"}
```

Sent when a player leaves the room. Receivers remove the player at once.

## 3. Nostr transport

### 3.1 Events

Every message is the `content` of a Nostr event (NIP-01):

| field | value |
|---|---|
| `kind` | **25713** (ephemeral range 20000–29999: relays forward but do not store it) |
| `tags` | `[["t", "stroopy-m1-" + lower(roomId)]]`, e.g. `stroopy-m1-796kqthw` |
| `content` | the message JSON (§2), serialised without insignificant whitespace |
| `created_at` | current Unix time in seconds |
| `pubkey`, `id`, `sig` | per NIP-01: `id = sha256(serialisation)`, `sig` = BIP-340 Schnorr signature of `id` |

`roomId` is the room id as 8 Crockford Base32 characters (§1.2).

Serialisation for the id (NIP-01): the UTF-8 JSON text of
`[0,<pubkey hex>,<created_at>,<kind>,<tags>,<content>]` without any
whitespace, where strings escape **only** `"` `\` and the control
characters `\n` `\r` `\t` `\b` `\f` as these two-character sequences; every
other character (including other control characters and non-ASCII) is
written verbatim. Hex strings are lower case.

Production signatures use 32 random bytes as BIP-340 auxiliary randomness.
The vectors use 32 zero bytes, which makes signatures reproducible.

### 3.2 Keys

A player creates a fresh random secp256k1 secret key when entering a room
and discards it when leaving. Keys are never stored and never linked to a
person.

### 3.3 Relays

- The room's relays are the Nostr entries of its invitation. The creator
  takes them from its relay setting: the user's list, or the app's default
  list if the user has none (the first 8 of either).
- Every player uses **exactly the room's relays**, whatever its own relay
  setting is. That setting only matters when creating a room.
- A player connects to every relay of the room, **publishes every event to
  all** of them, and subscribes on all of them with
  `["REQ", <id>, {"kinds":[25713], "#t":[<room tag>]}]`.
- Received events are **deduplicated by `id`**. Events with an invalid `id`
  or signature are dropped. The player's own events are ignored.
- Lost connections are retried with backoff (1 s doubling up to 30 s).
- The `OK`, `EOSE`, `NOTICE` and `CLOSED` relay messages are informative.

### 3.4 Default relays

Every app ships a default relay list for creating rooms. The list is not
part of this spec, because relays come and go. Recommended lists, with the
date they were chosen, are kept in
[`docs/design/nostr-relays.md`](../../design/nostr-relays.md). Apps take
the newest one.

## 4. Room behaviour

- **Presence**: a player is in the room from its first message until `bye`
  or until **15 s** without any message.
- **Host**: the player whose `status` says `host: true`. If several do, the
  one with the lowest public key (hex, lexicographic). If no host has been
  present for 15 s, the present player with the lowest public key becomes
  host and says so in its next `status`.
- **Starting**: a guest starts a game (3-2-1-GO countdown, then play) when it
  receives a `start` from the host, or when the host's `status` shows a
  game the guest hasn't played yet and that isn't over for the host. A guest
  plays each game code at most once. A guest that is playing keeps playing
  its current game; it may join the newer one afterwards.
- **Compatibility**: the host offers only modes in rules versions that every
  present player lists in `rules`.
- **Results**: ranking by score (descending), then `reached` (descending).
  Rules §6 defines both. The network adds no tie-break by time.

## 5. Privacy

Messages are signed but **not encrypted**. Relay operators and anyone who
has the invitation can read names and scores. Apps must say so where the
player enters a name, and must not send anything else.
