# Backup v1

Status: **draft**. It is frozen once the first implementation passes all
vectors.

Backup version `B = 1`. This spec defines how an app's highscores and shared
settings are encoded as bytes and as a text code, so that a user can move
them to another device or another Stroopy implementation
([decision 0011](../../decisions/0011-backup-code.md)).
Conformance vectors: `docs/spec/test-vectors/backup/v1/`.

## 1. Record (bytes)

All multi-byte integers are big-endian.

| offset | size | field | meaning |
|---|---|---|---|
| 0 | 1 | `B` | backup version, `1` |
| 1 | 1 | `flags` | bit 0: a settings section follows the entries. Bits 1–7 must be 0 |
| 2 | 2 | `E` | number of highscore entries (0–65535) |
| 4 | 19·`E` | entries | §1.1 |
| … | … | settings | only if flags bit 0 is set: §1.2 |
| end−2 | 2 | `crc` | CRC-16/CCITT-FALSE over all preceding bytes (as in share code v1 §1) |

### 1.1 Highscore entry (19 bytes)

| offset | size | field | meaning |
|---|---|---|---|
| 0 | 1 | `mode` | mode id as defined by rules `R` (1–255) |
| 1 | 1 | `R` | rules version (1–255) |
| 2 | 8 | `seed` | u64 PRNG seed |
| 10 | 2 | `score` | u16, clamped to 65535 when encoding |
| 12 | 2 | `reached` | u16, clamped to 65535 when encoding |
| 14 | 4 | `time` | u32 Unix time in seconds (UTC) when the game ended |
| 18 | 1 | `eflags` | bit 0: the game was started from a share code (a challenge). Bits 1–7 must be 0 |

A reader keeps entries whose `mode` or `R` it doesn't support: it can still
store and export them, but not replay them.

### 1.2 Settings section

```
K: u8                          number of items
K × { key: u8, len: u16, value: len bytes }
```

Each key appears at most once. Keys:

| key | setting | value |
|---|---|---|
| 1 | language | UTF-8 BCP 47 tag in lower case, e.g. `en`, `de`. Length 0 = follow the system |
| 2 | colour-blind palette | 1 byte, `0` off or `1` on |
| 3 | vibration on failure | 1 byte, `0` off or `1` on |
| 4 | player name | UTF-8, at most 64 bytes, no control characters |
| 5 | Nostr relays | UTF-8, relay URLs (`wss://…`) separated by `\n`. Length 0 = use the default relays (protocol v1 §3.4) |

- Keys `6`–`127` are reserved for future shared settings. A reader **skips
  unknown keys** (using `len`), so they can be added without a new backup
  version.
- Keys `128`–`255` are reserved and must not be written.
- A known key with a wrong length or value (e.g. a boolean of `2`) makes the
  backup *invalid*. So do a repeated key and invalid UTF-8.
- A reader that doesn't support a setting or a value (e.g. a language it
  doesn't have) ignores that setting.

Writers emit settings in ascending key order and include every setting
they have.

## 2. Text code

```
text := "SYB" + decimal(B) + "-" + groups(base32(record[1..]))
```

`base32` and `groups` are the same as in share code v1 §2: Crockford
alphabet, big-endian bit string, zero padding bits, no padding characters,
groups of 4 joined by `-`.

### 2.1 Parsing

A backup can be long, and messengers or mail clients may wrap it. Input may
be any text. A reader:

1. finds the first match of `SYB([0-9]+)-`, case-insensitive;
2. reads `B`. If `B` is unsupported, it reports *unsupported backup
   version* (and stops);
3. collects the characters that follow: it skips `-` and whitespace, maps
   letters to upper case and the aliases `O→0`, `I→1`, `L→1`, and stops at
   the first character that is then not in the alphabet (or at the end of
   the input);
4. decodes the record **structurally**: the header gives `E` and whether a
   settings section follows, the section gives its length, so the record
   length `L` is known from the data itself. Exactly the first
   `ceil((L−1)·8/5)` collected characters belong to the code. Further
   characters are ignored, so text after the code does no harm;
5. fails as *invalid* if there are too few characters, if the padding bits
   of the last used character are not zero, if the CRC doesn't match, or if
   a flag or a settings value is invalid (§1).

## 3. Restoring (informative)

The product spec (`docs/design/product.md`, "Backup") defines the user
flow. Recommended merge: add the imported entries to the existing ones, drop
exact duplicates (all fields equal), then keep the top list per mode as
usual. Settings from the backup replace the current ones when the user
chooses to restore them.
