# Protocol v1

Status: **draft**. It is frozen once two implementations have played
against each other and pass all vectors.

Protocol version `P = 1`. This spec defines live multiplayer: rooms, the
messages players exchange, and how they travel over Nostr relays
([decision 0012](../../decisions/0012-nostr-first-protocol.md)). Other
transports (LAN, Bluetooth) will carry the same messages and get their own
section in a later version.
Conformance vectors: `docs/spec/test-vectors/protocol/v1/`.

Principle: **the network only reports, it never drives.** Every device
generates the sequence from the descriptor and runs its own timers (rules
`R`). Messages carry who is in the room, which game to play, and how far
everyone got.

## 1. Rooms

A **room** is a group of players who play the same games one after another.
It is identified by a **room id** of 40 random bits, written as 8 Crockford
Base32 characters (alphabet of share code v1 §2).

| form | example |
|---|---|
| room code (text, QR) | `SYR1-7K3M-Q9TD` |
| link | `stroopy://join?r=SYR1-7K3M-Q9TD` |

- Text: `"SYR" + decimal(P) + "-" + id[0..4] + "-" + id[4..8]`.
- Parsing: find the first match of
  `SYR([0-9]+)-([0-9A-Za-z]{4})-?([0-9A-Za-z]{4})`, case-insensitive.
  If `P` is unsupported, report *unsupported protocol version*. Map the 8
  characters to upper case with the aliases `O→0`, `I→1`, `L→1`; any other
  character outside the alphabet makes the code *invalid*.
- Apps also accept the bare id as typed by a user: the whole input,
  trimmed, matches `^[0-9A-Za-z]{4}-?[0-9A-Za-z]{4}$`, mapped the same way.
- There is no checksum. A mistyped code leads to an empty room, and the
  lobby says that nobody is there yet.

The player who creates the room is its **host**. The host chooses the mode
and starts games. Everybody else is a **guest**.

## 2. Messages

Messages are JSON objects (UTF-8). Every message has `"p": 1` and a `type`.
A receiver ignores messages with another `p`, unknown `type`s and unknown
fields. A message with a missing or mistyped required field is ignored.

A player is identified by the **sender key** of the transport (§3: the Nostr
public key), not by a field in the message.

### 2.1 `status`

Each player's complete state. Sent:
- when joining the room,
- every **5 s** (heartbeat),
- when the state changes, but no more often than every **500 ms** (the
  latest state is sent when the interval has passed),
- immediately when the player's game ends.

```json
{"p":1,"type":"status","name":"Ann","host":true,"rules":[1],"mode":1,
 "game":{"code":"SY1-040G-0000-0000-001A-03CT-T","n":12,"score":11,"over":false}}
```

| field | type | meaning |
|---|---|---|
| `name` | string | player name, 1–24 characters, no control characters (see below) |
| `host` | bool | the sender is the host |
| `rules` | array of int | rules versions the sender can play |
| `mode` | int | host only: mode selected for the next game. Optional for guests |
| `game` | object | optional; the sender's current or last game in this room |
| `game.code` | string | the game's share code without result (share code v1) |
| `game.n` | int | item/round shown now; when over: `reached` (rules §6) |
| `game.score` | int | current score; when over: final score |
| `game.over` | bool | the game has ended for this player |

`game` is omitted until the player has started a game in this room.

Validation: `name` is a string, `host` a bool, `rules` a non-empty array of
integers 1–255, `mode` (if present) an integer 1–255; `game` (if present)
has a string `code`, non-negative integers `n` and `score`, and a bool
`over`. Otherwise the message is ignored. A receiver cleans `name`: it removes
control characters (U+0000–U+001F, U+007F), trims white space and keeps
at most 24 Unicode code points. An empty result becomes `?`.

### 2.2 `start`

Sent by the **host** to start a game.

```json
{"p":1,"type":"start","code":"SY1-040G-0000-0000-001A-03CT-T"}
```

`code` is a share code without result (receivers ignore a `start` whose
`code` doesn't decode or carries a result, and one whose rules or mode they
can't play). Its seed is chosen at random by the
host. The host sends `start` only when it isn't playing itself, and starts
its own countdown when sending.

### 2.3 `bye`

```json
{"p":1,"type":"bye"}
```

Sent when a player leaves the room. Receivers remove the player at once.

## 3. Nostr transport

### 3.1 Events

Every message is the `content` of a Nostr event (NIP-01):

| field | value |
|---|---|
| `kind` | **25713** (ephemeral range 20000–29999: relays forward but do not store it) |
| `tags` | `[["t", "stroopy-p1-" + lower(roomId)]]`, e.g. `stroopy-p1-7k3mq9td` |
| `content` | the message JSON (§2), serialised without insignificant whitespace |
| `created_at` | current Unix time in seconds |
| `pubkey`, `id`, `sig` | per NIP-01: `id = sha256(serialisation)`, `sig` = BIP-340 Schnorr signature of `id` |

Serialisation for the id (NIP-01): the UTF-8 JSON text of
`[0,<pubkey hex>,<created_at>,<kind>,<tags>,<content>]` without any
whitespace, where strings escape **only** `"` `\` and the control
characters `\n` `\r` `\t` `\b` `\f` as these two-character sequences; every
other character (including other control characters and non-ASCII) is
written verbatim. Hex strings are lower case.

Production signatures use 32 random bytes as BIP-340 auxiliary randomness.
The vectors use 32 zero bytes, which makes signatures reproducible.

### 3.2 Keys

A player creates a fresh random secp256k1 secret key when entering a room
and discards it when leaving. Keys are never stored and never linked to a
person.

### 3.3 Relays

- A player connects to every relay in its list, **publishes every event to
  all** of them, and subscribes on all of them with
  `["REQ", <id>, {"kinds":[25713], "#t":[<room tag>]}]`.
- Received events are **deduplicated by `id`**. Events with an invalid `id`
  or signature are dropped. The player's own events are ignored.
- Lost connections are retried with backoff (1 s doubling up to 30 s).
- The `OK`, `EOSE`, `NOTICE` and `CLOSED` relay messages are informative.

### 3.4 Default relays

Unless the user changed the list, every app uses exactly:

```
wss://relay.damus.io
wss://nos.lol
wss://relay.primal.net
```

Players only meet if their lists share at least one working relay.

## 4. Room behaviour

- **Presence**: a player is in the room from its first message until `bye`
  or until **15 s** without any message.
- **Host**: the player whose `status` says `host: true`. If several do, the
  one with the lowest public key (hex, lexicographic). If no host has been
  present for 15 s, the present player with the lowest public key becomes
  host and says so in its next `status`.
- **Starting**: a guest starts a game (3-2-1-GO countdown, then play) when it
  receives a `start` from the host, or when the host's `status` shows a
  game the guest hasn't played yet and that isn't over for the host. A guest
  plays each game code at most once. A guest that is playing keeps playing
  its current game; it may join the newer one afterwards.
- **Compatibility**: the host offers only modes in rules versions that every
  present player lists in `rules`.
- **Results**: ranking by score (descending), then `reached` (descending).
  Rules §6 defines both. The network adds no tie-break by time.

## 5. Privacy

Messages are signed but **not encrypted**. Relay operators and anyone who
knows the room tag can read names and scores. Apps must say so where the
player enters a name, and must not send anything else.
