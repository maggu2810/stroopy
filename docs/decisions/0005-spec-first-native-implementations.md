# 0005: Spec-first, independent implementations

Status: accepted (2026-10-19)

## Context
We want Linux desktop, Android and iOS, and later Windows, macOS and TVs.
Options:
- (a) one cross-platform UI framework for everything (Flutter, Compose
  Multiplatform, React Native, Qt, …);
- (b) a shared core (e.g. Kotlin Multiplatform or Rust) with native UIs;
- (c) independent implementations, each idiomatic for its toolkit, held
  together by precise specs.

The game core is small (a PRNG, item generation, timing, scoring, encoding,
multiplayer messages). Most of the code is UI and platform integration (networking,
camera, haptics, sharing). With AI-assisted development, writing a small
core several times is cheap. Keeping several implementations **compatible**
is the hard part. No single framework covers every target well: iOS without
a paid Apple account is only reachable as a web app (decision 0010).

## Decision
Option **(c)**: independent implementations (one per toolkit, in
`apps/<stack>[-<platform>]/`) built from `docs/spec/`. One implementation may
cover several platforms (Qt: Linux and Android, decision 0006; web:
browsers and iOS, decision 0010), and a platform may have more than one.
Implementations share no code. Compatibility is enforced by
**language-neutral conformance vectors**
(`docs/spec/test-vectors/<area>/v<N>/*.json`), generated by an independent
Python reference implementation in `tools/reference/`. Every implementation's
test suite must load and pass them.

Rules:
1. Specs are normative. If an implementation and the spec disagree, the spec
   wins. Ambiguities are fixed in the spec first, then in all apps.
2. Every behaviour that affects interoperability (sequence, timing, scoring,
   game code, multiplayer, backup) has test vectors.
3. A change to any of these areas bumps its version (decision 0007).
   Implementations state which versions they support.

## Consequences
- + Each app uses its toolkit idiomatically, with no lock-in to one
  framework.
- + Independent implementations cross-check that the spec is unambiguous.
- − Features and bug fixes are done once per implementation. `docs/design/`
  is detailed enough to keep the apps consistent.
